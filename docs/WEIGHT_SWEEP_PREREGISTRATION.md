# Pre-Registration: Pattachitra Adapter-Weight Sweep (Overtraining/Recipe Hypothesis)

**Committed 2026-07-25, before the running sweep (`scripts/_pattachitra_weight_sweep.py`) has
reported any result.** This fixes the decision rule, the non-inferiority margin, and the required
reporting format in advance so the call cannot be adjusted after seeing which weight looks best.
Do not edit this file to match a result once the sweep has data — a change to the design itself
belongs in a new commit with its own rationale. The author of this file has not read
`reports/pattachitra_weight_sweep.json`'s contents beyond confirming the sweep process is still
running; no partial result from it informed anything below.

## Background — why this sweep exists

`docs/MODEL_VERDICT.md` §7.2 found the Pattachitra curated LoRA regresses `figure_preservation`
vs. `sdxl_base` at every tested checkpoint (500/1000/1500 steps), and §7.2's corrected finding is
that the raw regression is monotonic in steps (−0.0228 → −0.0444 → −0.0461) — the signature of
progressive overtraining. This raises a genuine, distinct question: is the checkpoint **broken**
(any application of it regresses figure preservation), or is it **over-applied** at the
`adapter_weights=[1.0]` scale every checkpoint has been scored at so far? `set_adapters` accepts
any weight in `[0, 1]`; lowering it blends the LoRA delta back toward `sdxl_base` without
retraining, which is why this is testable at zero cost and zero GPU-hour spend.

## The tautology this design must guard against

**Adapter weight → 0 converges to `sdxl_base` by construction.** At `weight=0` the LoRA
contributes nothing: `figure_preservation` diff → 0 (no regression, trivially) and
`style_adherence` diff → 0 (no lift, equally trivially) — both because the model *is* base at that
point, not because anything was fixed. **A weight at which `figure_preservation` "recovers" is
therefore not, by itself, evidence of a usable adapter** — every checkpoint recovers
`figure_preservation` in the limit, including a checkpoint that has learned nothing useful at all.
The only way to avoid mistaking "diluted back toward doing nothing" for "found the adapter's real
operating point" is to require a **joint** condition: recovery on the guardrail axis **and** a
genuine, significant gain on the axis the adapter exists to produce, at the same weight. A design
that checks `figure_preservation` recovery alone, or reports it before/separately from
`style_adherence`, cannot distinguish these two cases and is not used here.

## Joint decision rule (fixed now, applied mechanically once the sweep completes)

For each `(checkpoint, weight)` pair in `{curated500, curated1000} × {0.3, 0.5, 0.7, 1.0}`, paired
against the matched `sdxl_base` records (`n=90`, same paired-diff/SEM methodology as every other
endpoint in this project — SEM on the 90 per-pair differences directly):

- **`style_adherence` significantly positive:** `diff/SEM > +2.0`. Same threshold and same
  direction as `docs/PATTACHITRA_AB_PREREGISTRATION.md`'s original primary endpoint A — reused
  here rather than a new number invented for this sweep, so a low-weight point cannot pass by
  a weaker bar than the original evaluation required.
- **`figure_preservation` non-inferior — the numeric margin, stated now:** `diff/SEM >= -2.0`.
  This is the *same* guardrail already in force throughout §7 (`compute_pattachitra_ab_stats.py`'s
  `regressed = fp["diff"] < 0 and fp["diff_over_sem"] < -2.0`), not a newly-invented, more lenient
  margin chosen to make a low-weight point easier to pass. Reusing the existing guardrail is the
  whole point of a "joint" criterion — the bar for "not regressed" does not get relaxed just
  because a different knob (weight, not steps) is being varied.
- **A viable operating point requires BOTH conditions at the SAME weight.** Passing one axis at
  one weight and the other axis at a different weight does not count.

**Pre-registered outcomes, stated before the data is read:**

- **If at least one `(checkpoint, weight)` pair satisfies both conditions:** the earliest
  (highest) weight among the passing set that a future publication decision would need is
  reported as the candidate operating point, together with its full joint curve and MDEs (below).
  This would mean the checkpoint is over-applied/overtrained at `weight=1.0`, not intrinsically
  incapable of a positive characterization.
- **If NO `(checkpoint, weight)` pair satisfies both conditions:** the pre-registered conclusion is
  **"no viable operating point — the adapter has no useful regime at any tested weight."** This is
  stated as the conclusion *in advance* precisely so it cannot be softened after the fact if the
  data comes back this way. A weight where `figure_preservation` merely stops regressing while
  `style_adherence` also collapses toward zero is explicitly **not** a counter-example to this
  conclusion — see the tautology guard above.

## Required reporting format (fixed now)

1. **`style_adherence` and `figure_preservation` are reported together as a function of weight —
   the joint curve — never one axis in isolation, and never a headline stated on only one axis.**
   A table with weight as the row key and both axes as columns, for both checkpoints.
2. **MDE at 80% and 90% power is reported alongside every point estimate**, exactly as
   `compute_pattachitra_ab_stats.py` already does for the original checkpoint comparison — a
   result that fails to clear ±2×SEM is labeled "does not clear the bar, MDE = X" rather than a
   bare non-significant diff.
3. **`weight=1.0` reuses the already-generated, CUDA-corruption-audited records**
   (`reports/pattachitra_ab_base_comparison.json`, `docs/MODEL_VERDICT.md` §7.2(4)) rather than
   regenerating — this is a re-analysis of already-verified-clean data at that weight, not new
   evidence requiring its own integrity pass.
4. **`scripts/compute_pattachitra_weight_sweep_stats.py` implements this rule mechanically** (the
   `is_operating_point` check requires `sa["diff_over_sem"] > 2.0` and
   `fp["diff_over_sem"] >= -2.0` jointly, at the same weight) — the script was corrected to this
   exact rule as part of committing this pre-registration, before being run against complete
   sweep data.

## What this sweep does NOT decide

This sweep tests dosage (adapter weight), not the recipe's step/epoch schedule
(`docs/MODEL_VERDICT.md` §7.2(5), the effective-epochs finding) — the two are independent
hypotheses and are not conflated here. A "no viable operating point" result from this sweep does
not by itself validate or refute the epoch hypothesis; conversely, an operating point found here
would not retroactively change the epoch computation. Both are reported on their own evidence in
`docs/MODEL_VERDICT.md` §7.2. No training, no GCP spend, and no HF publish action is triggered by
this sweep regardless of outcome — those remain blocked on the read-only token and on GG's
approval per this project's standing rules, independent of these results.
